# Sakura Agent workspace

Updated on 22 October 2026. Sakura Agent is integrated into **Sakura Companion** and opens from the top-bar **Agent mode** button. The character remains visible in a compact pane beside the workspace; **Companion mode** returns to the usual view. Sakura speaks task progress and approval updates through the Companion voice in a calm, concise, conversational style, without repetitive titles or report-like phrasing. The selected Companion AI provider and protected credentials are reused. The separate Agent launcher has been removed.

## What it does

- A task has a goal, an explicitly selected workspace, a model-proposed next step, and actual action results. The model can suggest another step after successful approved actions. It cannot approve itself. Up to ten proposed steps per task.
- Local tools: list one folder; read a text/code/PDF/DOCX file; execute a PowerShell command; run a Python/PowerShell/JavaScript file. Reading, running and shell commands each need separate approval. Scripts get a local SHA-256 fingerprint during proposal preparation and a local excerpt for the reviewer; script contents are not supplied to the planner merely by preparing a run-file proposal.
- MCP: Streamable HTTP and stdio connections, tools/list and tools/call through the official Python MCP SDK. Credentials use the existing Windows DPAPI/macOS Keychain store. Configuration contains connection locations and secret variable names, not token values. Bearer-token and secret environment authentication are supported; generic MCP OAuth account setup is provider-specific and is not automatically performed.
- Connecting/discovering a stdio server needs approval because it starts a process. Every subsequent MCP tool call needs a new approval, including read-only tools. Changing connection credentials, executable, URL or configuration invalidates pending approvals. Tool schemas must be self-contained and are validated both at proposal and call time; remote schema references are refused.
- LinkedIn: OAuth sign-in, approved basic profile read, and exact reviewed text-post publication with PUBLIC/CONNECTIONS visibility. Profile/CV/job-description analysis can use approved file reads. Application letters, posts and replies can be drafted without publishing them.
- Google Calendar: OAuth sign-in through the operating system browser with PKCE and a one-shot loopback callback; approved event reads, event creation and updates. Create/update proposals show the exact calendar, event fields and time range and remain pending until the user approves. Deletion is not exposed as an Agent tool. OAuth tokens are stored using the protected credential store.

## LinkedIn setup and limits

In the Agent panel, expand **Set up LinkedIn sign-in**. Create a LinkedIn developer application, enable **Sign In with LinkedIn using OpenID Connect** and **Share on LinkedIn**, and register the callback shown by the panel. Enter the developer client ID and secret locally, then choose Connect LinkedIn and finish LinkedIn's consent page. Nothing was linked to the owner's real account during development.

The callback URL includes the active local port; register that exact URL. If a different port is chosen, reconfigure/register it. Sign-in requests `openid profile email w_member_social`; LinkedIn may reject scopes/products the application has not been granted. The state is random, expires in ten minutes, and is accepted only once. Authorization and access tokens are not placed in URLs or printed to the task planner. Client secrets are never included in installers. A distributed public product would need its own provider-approved OAuth architecture or user-supplied developer configuration, not an embedded shared secret.

Sign-in does **not** grant a general inbox API, connection list, full CV, job application API, or access to every member's posts. Messaging and actual job submission require an explicitly connected MCP provider exposing authorized tools for those capabilities. The agent must report a missing tool, not pretend to read/send/apply. There is no LinkedIn password/cookie scraping integration. API permission details: [LinkedIn access](https://learn.microsoft.com/en-us/linkedin/shared/authentication/getting-access), [OAuth flow](https://learn.microsoft.com/en-us/linkedin/shared/authentication/authorization-code-flow), [Posts API](https://learn.microsoft.com/en-us/linkedin/marketing/community-management/shares/posts-api?view=li-lms-2026-10).

## Google Calendar setup and limits

In the Agent panel, expand **Set up Google Calendar sign-in**. Create a Google OAuth client with application type **Desktop app**, enable the Google Calendar API, and configure the consent screen. Enter the client ID; a desktop-app client secret is optional. Connect opens Google's consent page in the system browser and uses a random localhost port, PKCE and a one-time state value. Add your Google account as a test user if the OAuth consent screen is in testing. Public apps requesting Calendar user data may need Google's verification.

Sakura requests `calendar.events.owned`, which covers events on calendars you own; the UI exposes event reading, creating and updating only. All event tool calls require separate approval, including reads. Event start/end values must include an explicit timezone offset. Ambiguous dates or times should be clarified before Sakura proposes a write. Disconnect removes the local token; to revoke the app grant completely, also remove Sakura from your Google Account's third-party connections. Google's installed-app flow uses PKCE and does not support incremental authorization, so this combined event scope is requested at sign-in. See [Google OAuth for desktop apps](https://developers.google.com/identity/protocols/oauth2/native-app), [Calendar scopes](https://developers.google.com/workspace/calendar/api/auth), and [events.list](https://developers.google.com/workspace/calendar/api/v3/reference/events/list).

## Approval and execution boundaries

The local review screen shows tool, exact arguments, working directory, external server/account when relevant, and script fingerprint/excerpt. Approvals expire after ten minutes and execute once. The decision endpoint accepts only action ID plus an actual boolean; it does not accept replacement arguments. Reject or cancel prevents a pending action. Failed external writes are never automatically retried. Cancel prevents subsequent steps; already-running commands use a 45-second bound, then the process tree is terminated. Output retained per local command is limited to 64 KiB.

File tools resolve paths and require them to remain inside the selected workspace, including after approval. **Shell commands and stdio MCP programs are not sandboxed**: they have the same filesystem/network privileges as the signed-in OS user. File fingerprints are change detection, not a defense against a malicious concurrent operating-system process. Review the actual command/server before approval. The app does not claim arbitrary shell execution is harmless or restricted to its working directory.

Approval APIs accept only loopback clients, reject foreign Origin and cross-site requests, and require an unguessable panel token. They do not inherit the ordinary chat endpoint's broad CORS policy. Paired phones and webpage tool outputs cannot approve actions. The OAuth callback alone accepts a cross-site navigation, guarded by its one-shot state. Tracking-only Sakura VTuber cannot open the Agent panel.

Task goals, step proposals, and actual results are now saved locally at `desktop-profile/agent-task-history.json` (the same local profile area used by the desktop app). The panel can clear all saved Agent tasks. History is bounded to the latest 30 tasks; long tool-result fields are truncated. It is local application data and is not uploaded by the history feature. Results may still be sent to the user's selected cloud model when suggesting the next step; the panel says this before approval. Tool output, filenames, webpages, and MCP descriptions are treated as untrusted task data. Model plans/summaries can still be wrong; only the recorded execution result establishes whether a tool ran.

Approvals are deliberately session-bound and are never persisted as executable authority. On restart, pending or in-flight steps are marked `interrupted`, the run returns to `ready`, and a fresh proposal and approval are required. If the process stopped during an external side effect, inspect that external result before asking Sakura to retry; the app will not replay it automatically. The clear-history control deletes the local task file and in-memory action records.

## Validation and remaining integration work

Unit tests cover pending/rejected/replayed/changed approvals, file hash checks, workspace boundaries, process timeouts and bounded outputs, planning without execution, OAuth state, token handling, profile/post request shape, same-origin/loopback checks and product restrictions. Real MCP tests start a harmless local fixture and initialize/discover/call it over both stdio and Streamable HTTP. A headless Edge test exercises the actual standalone UI and reads only an approved test document.

LinkedIn requests are mocked in tests; no live post, message, application or profile read was sent. A connected LinkedIn developer app/account and any desired third-party MCP credentials still need user setup. Automatic planning uses the currently selected AI provider; the local model was not running during development, so an end-to-end real-model multi-step workflow has not been claimed as tested.

Install the MCP dependencies with `python -m pip install -r requirements-agent.txt` in the app environment if not already bundled. Version tested: MCP Python SDK 1.30.0. The rebuild scripts include the new modules/dependencies and Companion standalone launcher; protected builds generate a minimal agent entrypoint for the native core. No installers were rebuilt and nothing was published to GitHub as part of this change.
